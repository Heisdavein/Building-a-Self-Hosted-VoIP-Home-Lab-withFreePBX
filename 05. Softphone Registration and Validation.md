# 05. Softphone Registration and Validation

Back to README | Previous: FreePBX web setup | Next: Packet Tracer lab

Creating an extension only creates an account on the PBX. A device has to register to it before calls can be placed or received. This guide covers installing MicroSIP, registering extension 1001 and validating the system with a test call.

## 1. Install MicroSIP

A softphone is an application that does the job of a VoIP desk phone using SIP over an IP network. I chose MicroSIP because it is free, lightweight, supports current SIP standards, has a simple interface and only asks for the fields needed to register, which keeps troubleshooting simple.

1. Download the Windows installer from the official MicroSIP website, `https://www.microsip.org`.
2. Run the installer and accept the defaults.
3. Launch MicroSIP. It opens with no accounts configured, which is expected.

## 2. Add the SIP account

Open **Settings, Accounts** and select **Add Account**.

| Field | Value |
| --- | --- |
| SIP Server | The FreePBX VM’s IP address (for example `192.168.1.xxx`) |
| Username | `1001` |
| Password | The SIP secret generated when the extension was created |
- **SIP Server** tells the softphone where the PBX is. A wrong address means registration requests go nowhere.
- **Username** is the extension number. It is not the FreePBX web administrator login.
- **Password** is the SIP secret. FreePBX compares it with the stored value for extension 1001.

SIP devices cannot guess missing information, so one incorrect value in any of the three fields prevents registration. I check each field before suspecting the server.

## 3. Registration

After clicking **Save**, MicroSIP contacted the PBX within seconds and the account status changed to show it had registered. Depending on the MicroSIP version the status reads Ready, Registered or Online.

What happens during registration:

1. MicroSIP sends a SIP `REGISTER` request to the FreePBX server.
2. FreePBX checks that extension 1001 exists.
3. The PBX verifies the SIP secret.
4. On success it records the softphone’s current IP address and marks the extension registered.
5. The PBX can now deliver incoming calls to that device.

A successful registration shows that the server is running, the network and bridged adapter work, the extension was created correctly and authentication between client and server succeeded.

## 4. Echo Test call

Instead of creating a second extension, I used FreePBX’s built-in Echo Test, an automated service that records the caller’s speech and plays it straight back.

1. In the MicroSIP dial pad enter `43`, FreePBX’s default Echo Test feature code.
2. Click the green **Call** button.

The PBX answers immediately because it is an automated service rather than another phone. The test confirms SIP registration works, call signalling works, audio travels from the client to the PBX and audio returns to the client.

## 5. Two-way audio

After the call connected I heard a short automated greeting. When I spoke into the laptop microphone, my voice was played back a moment later. That shows audio flowing in both directions, so both the signalling and media paths work.

How to read a failure:

- Greeting heard but no echo: possible RTP or firewall problem.
- Call fails entirely: likely a registration or SIP signalling problem.

## 6. Verify the call in the CDR

After ending the call I opened **Reports, CDR Reports** in the FreePBX web interface and located the Echo Test call. CDR stands for Call Detail Records, which hold a record of calls the PBX has processed. The entry shows the calling extension, destination, duration, date and time, and status. Its presence confirms the PBX handled the call from start to finish.

In production, CDRs are used to troubleshoot failed calls, monitor call volume, audit activity, measure duration and produce billing information.

## 7. End-to-end result

```
Windows 11 host
      |
VirtualBox hypervisor
      |
FreePBX virtual machine (FreePBX server)
      |
Extension 1001
      |
MicroSIP softphone
      |
SIP registration
      |
Echo Test (*43)
      |
Two-way audio
      |
Call logged in CDR
```

Each stage depends on the one before it. A mistake in the VM, networking, extension, authentication or softphone settings would have stopped the call. The successful Echo Test showed the whole chain working.

## Going further

The documented next step is a second extension, for example 1002, registered on another softphone (another computer or a phone on the same LAN). That would allow direct extension-to-extension calls and exploring voicemail, call transfer, call forwarding and ring groups. This was not done in this project.
